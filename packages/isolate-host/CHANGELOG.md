# @riftydev/isolate-host

## Unreleased

- Sandbox: an operation whose promise has not settled when `destroy()` is called rejects `ERR_ISOLATE_HOST_SANDBOX_DESTROYED` (a host op or a run already done could still resolve with the destroyed sandbox's data a microtask later).
- Sandbox: a host write refused with `ERR_ISOLATE_HOST_SANDBOX_FULL` restores the times of the file and of every directory above it too (the rollback left new `mtime`/`ctime` for the next run to see).
- Sandbox (external review round 3): `destroy()` waits for every call the sandbox placed through one event registered when the call is created (a destroy between a run's result and `exec`'s continuation returned while the isolate still ran); an isolate still on its worker 1 s after its result retires that worker (a worker that never reports `gone` holds nothing forever); a call that ends stopped sends its terminal frame and `gone` in one write (warm `runCode` under load no longer spawns cold workers for it); a request that cannot be sent whole rejects its call with the error (docs said rerun).
- Sandbox (external review round 2): `destroy` and a worker's slot wait for the run's isolate on every end (a new `gone` frame from the worker, after the terminal frame and the unwind; a `memory` end freed both at the result); the state is encoded before the call registers (a failing encode leaves no phantom call); `createSandbox` refuses a `maxFsBytes` below an empty sandbox's cost (`ERR_OUT_OF_RANGE`); `exec` args/options and `createSandbox` options are read at the call; a destroyed sandbox drops its run at once; README: `timeoutMs` covers the consumer's encode, the consumer memory rule is an upper bound (5 × S + 16 MiB).
- Sandbox (external review round 1): `destroy` waits for an isolate still stopping after a timed-out run; the operation queue keeps no result; input bytes are copied at the call; an unknown option name of `createSandbox`/`exec` is `ERR_INVALID_ARG_VALUE`; the sandbox object shows no internals; the consumer's memory per run is ≈ 4 × the state + 8 MiB (was ≈ 6.7 ×): the state is encoded per attempt and its base64 written in pieces.
- `runCode`: writing under `os.tmpdir()` works as in Node (the guest FS now starts with `/tmp`).
- `createSandbox(options?)` (ADR-0568): a live sandbox for one agent run — host `writeFile`/`readFile`/`list`/`remove` (bytes exact, paths resolved in the sandbox, `maxFileBytes`, `maxFsBytes`), `exec(path, {args, …runCode options})` runs `node <path> [args]` with `runCode`'s result plus `stateRefused`, `snapshot()` (ADR-0567 bytes) and `createSandbox({ snapshot })`, `destroy()`. Files are rifty's in-memory FS, restored into each run's fresh isolate and captured after it; a killed or lost run leaves the files of before it. Operations on one sandbox run one at a time in call order. The package root exports `createSandbox` beside `runCode`.
- `runCode` stderr for a fatal error is Node's report without its `<file>:<line>` header (inspected error, user frames at Node's positions, `Node.js` trailer), including a file `require`d from the code; parity `tests/node-file.test.ts`. An unhandled rejection's reason still reaches it as isolated-vm's copy (no own props, `[cause]` or subclass name; compat isolate-host.md).
- A closed result channel's grace decides after reading what the worker already sent: a consumer that was not scheduled no longer reports a worker's own exit as forced (`… after closing its result channel without a result`), and a worker whose result channel ended takes no new call and does not count as idle, so a call no longer spends its rerun on it and a healthy warm worker is no longer ended beside it (ADR-0563 Corrections 2026-11-22). Known gap declared: with a starved consumer the deadline follows read order, not send time (compat ⚠️). Tests: the clock, closed-channel and interval-churn cases no longer depend on host load; the interval-period bridge test runs on a fake host clock.
- `process.exit(n)` from a promise callback, `queueMicrotask` or `nextTick` of the code's synchronous run (`main().then(() => process.exit(0))`) exits n as in Node, and an uncaught throw from `queueMicrotask` exits 1 with its diagnostic (a non-`Error` value arrives wrapped, with a bundle frame: compat ⚠️ non-`Error` throw); before, both ended as `termination: 'timeout'`, the exit with rifty's internal `process exit requires an active control port` text on stderr. Output written after the exit (work already queued: another microtask, a due timer, a microtask from an `'exit'` listener) is dropped, as Node prints nothing; that work still runs (`backlog/runtime-js/node-eval-work-queued-at-exit-runs`).
- Add the per-call `allowSharedArrayBuffer` option to `runCode`. False removes the global for feature detection. Shared wasm backing buffers throw the named gap on access. Default true (ADR-0566).

- Known gaps declared (no behavior change): an unhandled rejection whose promise the GC collects before its task ends is lost — `exitCode: 0`, empty stderr where Node exits 1 (isolated-vm weak record, https://github.com/laverdet/isolated-vm/issues/589). README gives the guest-side workaround (handle every promise).
- Cross-review round 3: a lost call's rerun whose worker fails to start asynchronously (ENOENT, EAGAIN, EMFILE) rejects `ERR_ISOLATE_HOST_WORKER_LOST`; a worker's RSS allowance resets when it goes from idle to busy. README states how far a worker's RSS can go and how to retry `ERR_ISOLATE_HOST_WORKER_LOST` (at most once, counted against the source's limit).
- Cross-review rounds 1–2 (ADR-0563 §Corrections): a worker lost with no culprit reruns each call alone, where an exhaustion of the process (wasm, resizable buffers, ICU, timers) is that call's `memory`; at most one process per call in flight. An interval never ticks early. A spawn failure rejects its call without holding the consumer, and while rerunning a lost worker's calls rejects them `ERR_ISOLATE_HOST_WORKER_LOST` instead of throwing in the consumer.
- `runCode` runs in a pool of long-lived worker processes, up to 4 calls each, instead of a child process per call (ADR-0563): warm call p50 137 → 13 ms, 8 concurrent calls 1118 → 414 MiB (M3 Pro). API and result shape unchanged. A culprit's memory/time limit ends its own call; neighbours on its worker get their own result. A worker killed from outside no longer rejects its calls at once: they rerun once; a second loss, or a rerun past its deadline, rejects with `code: 'ERR_ISOLATE_HOST_WORKER_LOST'` (no worker stderr in the message). The RSS ceiling is per worker: 256 MiB + 3 × the sum of its calls' `memoryLimitMb`. Idle workers do not keep the consumer alive.
- Intervals keep pace and period as in Node: a slow interval no longer delays later timers (a 1000 ms timeout after a 10 ms callback at 1 ms: 8.8 s → ~1.0 s), and 20000 × `setInterval(f, 1)` runs instead of ending as `termination: 'memory'` (ADR-0558 Decisions 2026-11-19).
- The guest's `performance.now()`/`timeOrigin` start at the run's bridge setup in the child, not at the child process start (closer to a fresh `node -e`; cross-review 2026-11-18, ADR-0558).
- The guest bundle and the bridge validation come from `@riftydev/isolate-guest` (ADR-0558); `dist/guest.js` is that package's bundle, copied. `runCode` API and install unchanged (the guest clock origin moved: line above). If delivering a timer expiry ever throws, the child now ends that timer instead of throwing in its own event loop.
- New package (ADR-0557): `runCode(code, options?)` runs `code` like `node -e` in a fresh rifty runtime inside an isolated-vm V8 isolate in a disposable clean-env child process; `{stdout, stderr, exitCode}` plus `termination: 'timeout' | 'memory'` and `truncated`.
