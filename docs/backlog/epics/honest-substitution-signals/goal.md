## Outcome

The honesty infrastructure built by the shadow-substitution series (recipe v2
admission, loud `NotImplementedError` gaps, compat pages for esbuild and sass,
eddy fast path with standard-install fallback) reaches the user's eyes at the
four surfaces where it currently stops short. No new mechanism: each slice
routes an existing fact to the surface a real-Node developer would read it from.
Faithful-runtime payoff: the substituted tree behaves like the real package
where it can (declarations), and every divergence names itself.

## User scenario

A developer imports a Vite 7.3.6 project whose `package.json` lists
`esbuild@^0.28.0` and `lightningcss@^1.30.0`, with the eddy resolver
unreachable on their network.

1. `npm install` prints in the terminal why the fast path declined (the same
   reason text that today only reaches `console.warn`) and completes the
   standard install, reporting `npm: installed N package(s) in …` as before.
   A from-scratch open of a template with preset pins — eddy's main path —
   runs the same `npm install` automatically in the terminal
   (`project-runtime-acquisition.ts:9-22`), so the same line appears there.
2. They open `scripts/build.ts` with `import { build } from 'esbuild'`. The
   installed `node_modules/esbuild` carries the `types` entry and
   `lib/main.d.ts` real esbuild publishes, so `tsc` in real Node and the
   in-browser TS language service resolve the same declarations.
3. They open the lightningcss compat page: it exists beside the
   esbuild and sass pages, generated by the same tool, naming the admitted
   request form (`semver-admits` against the trigger `lightningcss@1.32.0`),
   the acquired twin (`lightningcss-wasm@1.32.0`), the cited tests, and every
   loud gap.
4. They pin `esbuild@^0.21.0`. `npm install` fails with a message naming
   `esbuild@^0.21.0`, the exact version rifty substitutes (`0.28.0`), and the
   admission rule that refused it.
Done when all four run as tests on the default lane (terminal output test
covering the typed and the from-scratch-open automatic `npm install`,
installed-tree + type-resolution test, generated page + drift gate, admission
error test).

1. I1. When the eddy fast path declines, the `npm install` terminal output —
   whether typed or run automatically by a from-scratch project open — carries
   the decline reason; it is never console-only.
2. I2. The installed `esbuild` facade resolves TypeScript declarations exactly
   as the real `esbuild@0.28.0` package does (`types` entry + `lib/main.d.ts`
   byte-identical to the twin's), and the esbuild compat page states it.
3. I3. A `lightningcss` page exists under `docs/public/compat/`, is produced by
   `pnpm compat:generate` with the other substitution pages, indexed in the
   compat README, and names the admitted request form, the twin, the cited
   tests and every loud gap of the lightningcss substitution.
4. I4. A refused substitution request fails with a message naming the
   requested `<name>@<range>`, the exact substituted version and the admission
   rule (`exact-only` / `semver-admits`) that refused it — for every recipe in
   the builtin catalog.
